# GitHub Actions 및 Trivy 안내

이 문서는 PR 자동화와 Docker 이미지 취약점 검사가 어떤 순서로 실행되는지 설명합니다.

## PR 자동화 흐름

`config.yml`은 PR 이벤트를 받아 `docker-build.yml` 재사용 워크플로를 호출합니다.

| PR 이벤트 | 이미지 빌드 및 검사 | PR 본문 갱신 |
| --- | --- | --- |
| `opened` | 실행 | 실행 |
| `reopened` | 실행 | 실행하지 않음 |
| `synchronize` | 실행 | 실행하지 않음 |
| `ready_for_review` | 실행하지 않음 | 실행하지 않음 |
| `closed` | 실행하지 않음 | 실행하지 않음 |

PR 본문 갱신은 `opened` 이벤트에서만 수행합니다. 이때 검사 작업이 성공하거나 건너뛰어진 경우 `TRIVY_REPORT`를 PR 템플릿의 `__TRIVY_REPORT__` 위치에 넣습니다.

## 이미지 빌드 및 검사

`docker-build.yml`은 `workflow_call`로 호출되는 재사용 워크플로입니다.

1. `ai`, `embedding`, `ingest` 타깃을 matrix job으로 각각 빌드합니다.
2. 각 이미지를 `ci-<target>:sha-<commit SHA>` 태그로 로드합니다.
3. 같은 job에서 Trivy가 해당 로컬 이미지를 검사하고 JSON 결과를 생성합니다.
4. 각 결과를 `trivy-<target>` artifact로 업로드합니다.
5. 요약 job이 세 artifact를 모아 취약점 수와 주요 항목을 만들고, 이를 재사용 워크플로 출력 `summary`로 반환합니다.

빌드와 이미지 검사가 같은 matrix job 안에 있으므로 로컬 이미지를 다른 job이나 별도 워크플로로 전달할 필요가 없습니다. matrix job은 GitHub Actions 러너 가용성에 따라 병렬로 실행됩니다.

Trivy는 JSON 형식으로 결과를 저장합니다. `exit-code: '0'` 설정은 취약점 발견 자체가 검사 job을 실패시키지 않도록 합니다. 이미지 빌드나 검사 실행 자체의 오류까지 무시하는 설정은 아닙니다.

## PR 리포트 읽기

리포트에는 검사 대상, CRITICAL/HIGH/MEDIUM/LOW별 발견 수, 심각도 우선으로 정렬한 주요 항목 최대 10건이 포함됩니다. 상세 항목은 CVE, 심각도, 이미지, 패키지, 설치 버전, 수정 버전으로 표시됩니다.

취약점 수는 Trivy가 보고한 패키지별 취약점 항목의 수입니다. 같은 CVE가 여러 패키지 또는 이미지에 영향을 주면 여러 건으로 집계될 수 있으므로, 고유 CVE 개수와는 다를 수 있습니다. 수정 버전이 제공되지 않은 항목은 `수정 버전 없음`으로 표시됩니다.

## 별도 이미지 보안 워크플로

`image-security.yml`은 `main` 브랜치의 지정된 파일 변경과 수동 실행을 위한 별도 워크플로이며, 현재 PR 자동화 경로에서는 호출되지 않습니다. PR의 `TRIVY_REPORT`는 `docker-build.yml`의 빌드 결과에서 만들어집니다.

현재 `image-security.yml`은 `ci-<image>:sha-<commit SHA>` 이미지를 검사하도록 설정되어 있지만, 해당 워크플로 안에서 이미지를 빌드하거나 레지스트리에서 가져오는 단계는 없습니다. 이 워크플로를 실제 이미지 검사에 사용하려면 검사 시점에 이미지가 같은 runner에 있거나 접근 가능한 레지스트리에 있어야 합니다. `docker-build.yml`의 로컬 이미지는 별도 워크플로로 자동 전달되지 않습니다.
